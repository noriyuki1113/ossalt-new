Difyは、生成AIを使ったアプリを、プログラムをほとんど書かずに作れる開発基盤です。チャットボット、社内文書に答えるAI、複数の処理をつないだワークフローなどを、画面上で部品を組み合わせて作ります。公式は「LLMアプリの開発プラットフォーム」と説明しています。クラウド版のほかに、自社のサーバーで動かすこともできます。

### できること

公式のREADMEにある、主な機能です。

- **ワークフロー**：AIへの問い合わせ、条件分岐、外部のAPIの呼び出しなどを、画面上のキャンバスで線でつないで、一連の処理を作ります。作ったものは、その場で試せます。
- **多くのAIモデルに対応**：OpenAIのGPT、Mistral、Llama3など、数百のモデルに対応するとされています。OpenAI互換のAPIを持つモデルや、[Ollama](/tools/ollama/)などで自前で動かすモデルにもつなげられます。
- **プロンプトの作成画面**：AIへの指示文（プロンプト）を作り、モデルごとの結果を見比べられます。チャット形式のアプリには、読み上げなどの機能も足せます。
- **社内文書を使った回答（RAG）**：マニュアルや規程などの文書を取り込み、その内容をもとにAIに答えさせます。PDFやPowerPointなど、よくある形式の文書から、文字を取り出す機能が最初から入っています。
- **エージェント**：AIが自分で判断して、コマンドの実行やファイルの操作を進める仕組みです。専用の隔離された環境（サンドボックス）で動きます。ツールは、公式のマーケットプレイス、MCPサーバー、自社のAPIなどから足せます。
- **運用の記録と分析**：ログや性能を記録して、本番での利用の結果をもとに、プロンプトやデータを改善できます。Opik・Langfuse・Arize Phoenixとの連携も紹介されています。
- **APIとして使う**：作ったアプリには、対応するAPIが付きます。自社のシステムから呼び出せます。

### 3つの使い方

公式は、次の3つの提供形態を案内しています。

- **クラウド版（Dify Cloud）**：サーバーを用意せずに試せます。料金プランは、公式の料金ページで確認します。
- **自前で動かす（Community Edition）**：このページで中心に扱う方法です。
- **Enterprise版（有料）**：自前での運用に加えて、SSO、役割ごとの権限（RBAC）、サポートの保証（SLA）が必要な組織向けです。

### 向いている人・向いていない人

- **向いている**：社内向けのAIチャットや問い合わせ対応を、エンジニアでない担当者も含めて作りたいチーム。入力する情報を外部に出したくないので、自社の環境で動かしたい場合。
- **向いていない**：ChatGPTのように「すぐに質問して使う」だけが目的なら、[Open WebUI](/tools/open-webui/)のようなチャット画面のほうが手軽です。AIを使わない業務の自動化が中心なら、[n8n](/tools/n8n/)も候補になります。
- **似たツールとの違い**：[Langflowとの違い](/compare/dify-vs-langflow/)、[RAGFlowとの違い](/compare/dify-vs-ragflow/)でも比べられます。

### 自分のサーバーで動かす

**必要な環境**（公式の導入手順）

- CPUは2コア以上、メモリは4GiB以上です。
- Docker Compose 2.24.0以降が必要です。Linuxでは、Docker 19.03以降も必要です。
- Macの場合は、Docker Desktopの仮想マシンに、2つ以上の仮想CPUと8GiBのメモリを割り当てます。Windowsは、WSL 2を有効にしたDocker Desktopを使います。

**起動までの流れ**

1. Difyのソースコードを、最新のリリースの版で取得します。
2. `docker` フォルダーで、設定ファイルの見本（`.env.example`）を `.env` にコピーします。
3. エージェント用のサンドボックスの合言葉（トークン）を作り、`.env` の `DIFY_AGENT_LOCAL_SANDBOX_AUTH_TOKEN` に設定します。**これがないと、エージェントの機能が起動しません。**
4. `docker compose up -d` で起動します。
5. ブラウザで、サーバーの `/install` を開いて、管理者のアカウントを作ります。

起動すると、核になる7つのサービスと、データベース（PostgreSQL）・キャッシュ（Redis）・ベクトルデータベース（Weaviate）・Webサーバー（nginx）・サンドボックスなど、8つの付属のコンテナが動きます。**データベースなど複数のコンテナが動くため、メモリには余裕のあるサーバーを用意しましょう。** 初期設定を一度だけ行うコンテナ（`init_permissions`）は、終わると停止するのが正常です。

### つまずきやすい点

公式のFAQにある、導入時の注意です。

- **取得の失敗**：最新の版を調べるときにGitHubのAPIを使うため、制限にかかると「Remote branch null not found」というエラーになります。その場合は、版の番号を指定して取得します。
- **ログインが維持されない**：画面とAPIを、別のサブドメイン（例：app.example.com と api.example.com）に分けて、リバースプロキシの後ろに置くと、ログインしても次の操作で切れることがあります。
- **ログインのメールが全員ブロックされる**：Cloudflareなどのプロキシの後ろに置くと、全員が同じ送信元の住所に見え、まとめて制限される場合があります。nginxの設定で、利用者本来の住所を渡すようにします。

### 運用で必要なこと

- **更新**：更新の手順は、版ごとに違います。リリースのページにある、対象の版の更新の案内に従います。更新後は、設定ファイルの見本（`.env.example`）と自分の `.env` を見比べて、追加・変更された項目を反映します。`docker-compose.yaml` を自分で変えている場合は、新しい版のファイルに、変更を移し直します（新しい版で、必要なサービスが増えることがあるためです）。
- **バックアップ**：公式のFAQは、更新の前に、Difyのフォルダー全体をコピーしておくことを勧めています。データベースなどのデータの守り方は、自社の運用に合わせて決めます。
- **外部のAIサービスの費用**：OpenAIなどの外部のAIを使う場合は、その利用料が別にかかります。Difyを自前で動かしても、AIの利用料はなくなりません。

### 注意点：ライセンス

ライセンスはApache-2.0をもとにした、独自の条件つきです。一般的なApache-2.0とは異なります。公式のライセンスの文では、次のように書かれています。

- **商用で使えます**：企業の開発基盤や、他のアプリの裏側のサービスとして使えます。ただし、次の条件に当たる場合は、**商用ライセンスを別に取る必要**があります。
- **マルチテナントのサービス**：Difyの書面での許可なく、Difyのソースコードを使って、複数の顧客（テナント）を同じ環境で運用することはできません。Difyでは、1つのワークスペースが1つのテナントです。
- **ロゴと著作権の表示**：Difyの画面（フロントエンド）を使う場合、コンソールやアプリのロゴと著作権の表示を、消したり変えたりすることはできません。画面を使わない利用には、適用されません。
- **貢献者の同意**：コードを提供する人は、提供元が契約を厳しく、または緩く変えられること、提供したコードが、クラウド事業を含めて商用に使われることに、同意する必要があります。

**社内で使うだけ**なら多くの場合は問題になりませんが、外部の顧客に提供する場合は、公式のライセンスの文を確認してください。この解説は、個別の利用の法的な可否を保証するものではありません。
