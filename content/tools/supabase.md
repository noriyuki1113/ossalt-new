Supabaseは、Webアプリやスマートフォンアプリの裏側（バックエンド）に必要な機能を、まとめて提供する開発基盤です。Firebaseの代わりとしてよく比べられます。中心にあるのは、広く使われているデータベースのPostgreSQLです。公式は「Postgresの開発プラットフォーム」と説明しています。クラウド版のほかに、自前のサーバーで動かすこともできます。

### できること

公式のREADMEにある、主な機能です。

- **データベース**：PostgreSQLを、画面とAPIから扱えます。
- **ログインと権限**：メールアドレスとパスワードや、外部のアカウントを使ったログインの仕組みと、アクセス権限の管理を用意できます。
- **自動で作られるAPI**：データベースの表から、RESTとGraphQLのAPIが自動で作られます。データの変更を、アプリにすぐ知らせる機能（リアルタイム）もあります。
- **関数**：データベースの中で動く関数と、サーバー側で動かす関数（Edge Functions）があります。
- **ファイルの保存**：画像などのファイルを保存し、アクセスの権限をPostgresで管理します。
- **AI向けの機能**：ベクトル（埋め込み）を扱う道具があり、AIの検索や文書検索に使えます。
- **管理画面（ダッシュボード）**：表やユーザーを、画面から操作できます。

### Firebaseとの違い

- **データベースの種類**：FirebaseのFirestoreはドキュメント型のデータベースですが、SupabaseはSQLで扱うリレーショナルデータベース（PostgreSQL）です。表どうしの関係を扱うデータに向いています。
- **自前で動かせる**：Supabaseはオープンソースなので、自社のサーバーで動かすこともできます。公式は、既存のオープンソース（MITやApache 2などのライセンスのもの）を組み合わせて作っていると説明しています。
- **データベース本体**：中心にあるのは、標準的なPostgreSQLです（公式のREADMEの説明）。

### 自分のサーバーで動かす

**必要な環境**（公式の導入手順）

| 項目 | 最低 | 推奨 |
|---|---|---|
| メモリ | 4GB | 8GB以上 |
| CPU | 2コア | 4コア以上 |
| ディスク | 40GBのSSD | 80GB以上のSSD |

開発や、小〜中規模の本番に向く、とされる最低ラインです。Realtime・Storage・Edge Functionsなど、使わないサービスは、設定から外して必要な資源を減らせます。

**導入の流れ**

1. Linuxのサーバーなら、公式のセットアップのスクリプト1つで、Dockerの導入、設定ファイルの取得、パスワードや鍵の自動生成、URLの入力までできます（Debian・Ubuntu・RHEL系に対応）。ほかのOSでは、設定ファイルを取得して、手動で設定します。
2. **初期設定のままのパスワードや鍵では、絶対に起動しないでください**（公式が強い警告を出しています）。付属のスクリプトで、安全な値を作ります。
3. `run.sh start`（中身は `docker compose up -d --wait`）で起動します。
4. 管理画面（Studio）は、HTTPのベーシック認証で守られます。安全なパスワードを、起動の前に設定します。

### クラウド版との違い（自前で動かすと使えないもの）

公式の説明では、自前で動かすSupabaseは、**1つのプロジェクトとして動きます**。管理画面で、複数の組織やプロジェクトを扱えません。次のものは、クラウド版にあって、自前では使えません。

- ブランチ（開発用の分岐）
- ログ以外の詳しい指標
- 管理されたバックアップと、任意の時点への復元（PITR）
- 分析機能とベクトル用のバケット、ETL
- Management API

標準の構成では、ログと分析の機能も入っていません。必要なら、追加の設定ファイルで有効にできますが、必要な資源が増えます。

### 運用で自分が担うこと

公式が「自前で動かす場合の責任」として挙げているものです。

- サーバーの用意と保守
- セキュリティの対策（OSとサービスの更新を含む）
- サービスの設定と管理
- PostgreSQLの保守
- 高い可用性と、規模の拡大
- **バックアップと、障害からの復旧**
- 監視と稼働の維持

更新は、公式が、動作を確認した組み合わせを、**おおよそ月に1回**公開しています。個々のサービスの版を自分で変えることもできますが、互換性は保証されません。自前で動かすSupabaseは、公式のサポートではなく、コミュニティ（GitHubのDiscussions・Discord）によるサポートです。

### 向いている人・向かない人

- **向いている**：SQLでデータを扱いたい開発チーム。データの置き場所を自社で決めたい組織。
- **向かない**：サーバーの運用を担当できる人がいない場合（クラウド版のほうが合います）。クラウド版の機能（自動のバックアップ、複数プロジェクトなど）が必要な場合。

### 注意点

- **Supabase CLIでの「ローカルの環境」は、自前での運用ではありません。** 開発とテスト用で、本番向けに強化されておらず、外部からのアクセスを受けてはいけない、と公式は説明しています。
- **ファイルの保存先**：標準では、サーバーのファイルシステムに保存されます。S3互換のストレージにも変えられます。Macでは、Dockerの制限のため、保存先の設定を変える必要がある場合があります。
- **秘密の値の管理**：本番では、設定ファイル（.env）に置くだけでなく、秘密の管理サービスを使うことを、公式は強く勧めています。
- **データの削除**：公式の初期化の手順（`reset.sh`）は、データベースとストレージを含む、すべてのデータを削除します。実行の前に、対象を確認してください。
- **ライセンス**：ライセンスはApache-2.0です。内部で使う各部品には、それぞれのライセンスがあります。

[Firebaseの代替](/alternatives/firebase/)のページで、ほかの候補も比べられます。
