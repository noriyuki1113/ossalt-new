# OSSALT Quality Intelligence（OSS詳細ページの品質監査）

OSS詳細ページ（`/tools/<id>/`）を全件、同じ基準で監査し、問題と改善の順番を出す仕組み。**判定はルールベース**（LLM・有料API・外部サービスを使わない）で、**ビルド済みの `out/` と掲載データ・手書きの解説だけを読む**（公開サイトには接続しない）。

## 使い方（iPhoneのClaude Codeから、短い指示で）

| 言いたいこと | Claudeが実行すること |
| --- | --- |
| 「OSSALTの全件品質監査を実行して」 | `npm run build` → `npm run qi:full` |
| 「前回から変更されたページだけ監査して」 | `npm run build` → `npm run qi:diff` |
| 「n8nの詳細ページを再監査して」 | `npm run build` → `npm run qi:one -- n8n`（前回との比較つき） |
| 「品質の低いページを20件出して」 | `npm run qi:report -- --top 20` |
| 「前回の監査から改善されたページを教えて」 | `npm run qi:report -- --improved` |
| 「P0問題の一覧を出して」 | `npm run qi:report -- --p0` |
| 「ダッシュボードを見せて」 | `reports/quality/latest/dashboard.html` を送る |

- 監査はビルド済みの `out/` を読む。**先に `npm run build`**（データやテンプレートを変えたあとは必須）。
- 全件監査は数秒〜数十秒（共通テンプレートの表示検査を含めると約1分）。差分・個別も同じ計算をするので、結果は全件と一致する。

## 出力と保存先

| 出力 | 場所 | Git |
| --- | --- | --- |
| 台帳（CSV）・詳細（JSON）・要約（Markdown）・ダッシュボード（HTML） | `reports/quality/<監査ID>/`、最新は `reports/quality/latest/` | 管理外（毎回作り直せる） |
| 履歴（点数・評価・警告・不足の項目・入力のハッシュ） | `quality/history/<監査ID>.json`、一覧は `quality/history/index.json` | **保存する**（全件監査のときだけ書く） |
| 修正状況（改善待ち・対応中・修正済み・確認済み） | `quality/fixes.json` | 保存する（手で更新） |

- 監査IDは「日付-短いハッシュ」。前回の履歴と比べて、改善・悪化・入力の変更を出す。
- **Search Console の数値は、手元のCSV（`agency/data/*/ページ.csv`）があるときだけ優先度に使い、`reports/`（Git管理外）にだけ出す。** 公開リポジトリの履歴には入れない。

## 評価の基準（`qi-1.0`、`scripts/quality/qi-lib.mjs`）

100点満点＝独自性・実用性30／正確性・根拠25／比較・意思決定20／SEO・検索意図15／使いやすさ10。A 85以上・B 70以上・C 50以上・D 50未満。

| 領域 | 項目 | 判定 |
| --- | --- | --- |
| 独自性・実用性 | U1 手書きの解説がある（10）・U2 600字以上（5）・U3 向いていない場合・注意点（5）・U4 ほかの解説と重複していない（文字6-gramの類似度0.5未満、5）・U5 導入の判断材料（5） | 自動 |
| 正確性・根拠 | R1 ライセンス表記がデータと一致（5）・R2 公式サイトとリポジトリへのリンク（5）・R3 取得元がミラーでない（5）・**R4 公式資料と照合した記録（5、記録が無ければ「未確認」）**・R5 説明文・解説・共通テンプレートの数値と用語の食い違いがない（5） | 自動（R4は編集の記録） |
| 比較・意思決定 | **C1 代替の種類の分類（5、無ければ「未確認」）**・C2 向いている人／向いていない人の要約（5）・C3 比較・代替ページへの導線（5）・C4 代替対象がSaaSでOSSではない（5） | 自動（C1は編集の記録） |
| SEO・検索意図 | S1 title・description・canonical・h1（5）・S2 indexとサイトマップの整合（4）・S3 構造化データ（3）・S4 3ページ以上からの内部リンク（3） | 自動 |
| 使いやすさ | X1 共通テンプレートの表示検査（代表ページで横スクロール・アクセシビリティ・コンソール、6）・X2 データの取得日の表示（4） | 自動（代表ページ） |

ルール
1. **検査できない項目は0点にしない**。「未確認（unknown）」として配点の母数から外す。確認できた配点が80%未満なら「暫定」、50%未満なら「未評価」で、総合点を出さない。
2. **未検証と不合格を区別する**。R4（公式資料との照合）が無いページは、点数が高くても**Bまで**（Aは根拠つきのページだけ）。
3. **重大な誤情報の疑いは、点数とは別に「警告」として出す**（ミラーからの取得、OSI承認でないのに「オープンソース代替」、件数の食い違い、代替対象がOSS、アーカイブ、リンク切れ、サイトマップとの不整合など）。
4. 共通部分（ナビ・スペック表・健全度の説明・定型のFAQ・関連一覧・広告枠）は、独自の内容として数えない。独自性は手書きの解説だけで見る。FAQは「ツール名を除いて20ページ以上で同じ文」を定型として、割合を出す。
5. 同じ入力と同じ基準なら、同じ結果になる（監査IDと日時以外）。基準を変えたら `RULES_VERSION` を上げる。

優先度：P0＝重大な警告（共通テンプレートの誤表記・ミラー・リンク切れ・サイトマップの不整合など）／P1＝D評価、または中程度の警告／P2＝C評価・未評価／P3＝それ以外。同じ優先度の中では、Search Console の表示回数（手元にある場合）の多い順。

## 前提と不確実性
- 本番のデプロイ元：既定のブランチ `claude/ossalt-jp-setup-deploy-tsv3x8` への push で `deploy-pages.yml`（GitHub Pages）が動き、Cloudflare Pages（`ossalt-new.pages.dev`）にも同じブランチが配信される。`ossalt.jp` がどちらを配信しているかは、DNS（Cloudflare）の設定を見ないと確定できない（本番反映確認の結果では、両方とも同じ内容）。
- 監査はローカルのビルド結果を見るので、**本番のキャッシュや、デプロイ前の状態は反映しない**。
- 公式資料との照合（R4）は、`raw.githubusercontent.com` の README・LICENSE で行った範囲だけ。公式ドキュメントのサイトには接続できないことがある。

## しないこと
有料API・LLM API・外部のクローリングサービスの利用、新しい定期実行（GitHub Actions）、常時動くサーバー、データベースの新設、本文の一括書き換え、noindexの一括追加、公開サイトへの管理画面の追加。
