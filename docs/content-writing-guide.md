# 解説の書き方と、毎週の追加の手順

ossalt.jp の手書きの解説（`content/`）を書くときのルールと、毎週の自動の追加（Claudeの定期実行）の手順です。
**人が書くときも、Claudeが書くときも、このルールに従います。**

## 毎週の追加の手順（定期実行のClaudeが行うこと）

1. **最新にする**：`git pull origin claude/ossalt-jp-setup-deploy-tsv3x8`（このブランチが公開用）
2. **点検の結果を先に直す**：`node --experimental-strip-types scripts/content-check.mjs` を実行し、`docs/content-check.md` の「要対応」があれば、最優先で直す。「要確認」も、データと照らして直せるものは直す。
3. **候補を選ぶ**：`node --experimental-strip-types scripts/content-targets.mjs --n 10` の上位から、**ツール5件・比較5組**を選ぶ。
   - 情報が少なく、正確に書けないものは飛ばして次の候補にする（無理に書かない）。
   - 比較は、2つのツールの違いがはっきり書ける組を選ぶ。
4. **書く**：下の「書き方」に従う。`updated` は今日の日付。
5. **確かめる**（すべて通らなければ公開しない）
   - `npm test`（すべて合格）
   - `NEXT_TELEMETRY_DISABLED=1 NODE_OPTIONS="--max-old-space-size=1150" npx next build`（成功）
   - 新しい解説の中のサイト内リンクが、すべて `out/` に存在すること
   - `node --experimental-strip-types scripts/content-check.mjs` で、新しい「要対応」が出ていないこと
6. **公開**：ビルドで変わった `public/data` と `data-source/star-history.json` は `git checkout --` で戻してから、`content/` と `docs/content-check.md` だけをコミットし、`git pull --rebase` のうえ push する。pushするとサイトに自動で公開される。
   - コミットの文面は「解説の週次追加：ツール5件・比較5組（YYYY-MM-DD）」とし、追加したものの名前を本文に並べる。
7. **報告**：最後に、追加したもの・直したもの・飛ばした候補とその理由を、短くまとめる。

**やらないこと**：プルリクエストを作らない。`content/` と `docs/content-check.md` 以外のファイル（プログラム、データ、設定）を変えない。外部への投稿や連絡をしない。

## 書き方の共通ルール

- **推測を書かない。** 数値・機能・ライセンスは、掲載データ（`public/data/tools.json`）か、各プロジェクトの公式の情報（README、ライセンスのファイル、公式ドキュメント）にもとづくものだけを書く。確かめられないことは書かないか、「公式の案内で確認してください」と案内する。
- **動かして確かめていないことを、確かめたように書かない。** 「速い」「軽い」などは、公式の説明であれば「公式の説明では」と書く。
- **データの「未確認」は「非対応」ではない。** 日本語の画面やDockerは、データで確認済み（`true`）のときだけ「確認できています」と書く。
- **ライセンス**：データのライセンス表記と一致させる。一般的なOSSライセンスでないもの（BUSL、Sustainable Use、MSCL、独自のライセンスなど）は、そのことを明記し、社内の利用とサービスとしての提供の違いを書く。
- **開発の状況**：アーカイブされたもの、1年以上更新がないものは、そのことを書く。おすすめとして紹介しない。
- **リンク**：サイト内のリンクは、実在するページだけ。未公開のブログ記事（`date` が今日より後）にはリンクしない。比較のページは、生成されている組（`scripts/content-targets.mjs` の一覧や `out/compare/`）だけ。
- **言葉づかい**：やさしい日本語で、1文を短くする。専門用語は、初めに短く説明する。「〜です・ます」で書く。
- **SaaSのままのほうがよい場合**や注意点を、必ず書く（よいことだけを書かない）。

## ツールの解説（`content/tools/<id>.md`）

```markdown
---
description: "〇〇とは、（何をするものか1文）です。（特徴1文）。できること、△△との違い、（注意点の要約）を解説します。"
updated: "YYYY-MM-DD"
---

〇〇（読み方）は、（何をするものかを2〜3文で）。

### できること

- **（機能）**：（説明）
- （4〜6項目。データで確認済みなら「画面の日本語翻訳と、Dockerでの導入方法を確認できています。」を最後に）

### △△との違い

（よく比べられるツールやSaaSとの違い。比較のページがあればリンクする）

### 注意点

- （導入・運用でつまずきやすい点を具体的に）
- ライセンスは〇〇です。

[□□の代替](/alternatives/<slug>/)のページで、ほかの候補も比べられます。
```

- 本文はおおむね1,500〜2,600バイト。見出しは `###` を使う（ページ側で `##` の見出しが付くため）。

## 比較の解説（`content/compare/<a>-vs-<b>.md`）

```markdown
---
description: "AとBの違いを比べます。（どちらも何の代替か）。（違いの要点1文）。"
updated: "YYYY-MM-DD"
---

**結論：（〇〇ならA、△△ならB）。**

- **Aを選ぶ場合**：（2〜3文）
- **Bを選ぶ場合**：（2〜3文）

**（違いの注意・選ぶときのコツ・共通の点など）**：（1〜2段落）

**ライセンス**：AはX、BはYです。

詳しくは[Aとは](/tools/a/)、[□□の代替](/alternatives/<slug>/)のページを参照してください。
```

- slugは2つのidをアルファベット順に並べたもの（`scripts/content-targets.mjs` の表示どおり）。
- 役割が違う組（例：エンジンと管理画面）は、「役割が違う・組み合わせることもある」とはっきり書く。
