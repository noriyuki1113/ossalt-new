# テストの書き方（OSSALT）

考え方は agent-skills の test-driven-development を、OSSALT向けに短くしたもの。

## どこに書くか
| 対象 | 場所 | 実行 |
|---|---|---|
| 純粋な関数・データの検証 | `src/lib/*.test.ts` | `npm test` |
| スクリプト | `scripts/*.test.mjs`（`scripts/quality/`、`mcp/test/`、`autodev/lib/` も同様） | `npm test` |
| ページの表示・転送・noindex・導線 | `e2e/*.spec.ts`（Playwright） | `npm run test:e2e`（PRではCI） |

単体テストは Node 標準の test runner（`node:test`）を使っている（テスト用の外部ライブラリは入っていない）。まず、副作用のない関数に切り出してテストする（例: `src/lib/editors-picks.ts` と `editors-picks.test.ts`）。

## バグを直すとき（先に失敗するテスト）
1. バグを再現するテストを書く。
2. **失敗することを確認する**（理由が、そのバグであること）。
3. 最小の修正で通す。
4. 全体（`npm test`）が通ることを確認する。

先に失敗を見ないテストは、何も保証していないことがある。

## 新しい振る舞い・新しいスクリプト
- 期待する結果を、先にテストに書く（赤）→ 実装（緑）→ 整える。
- 失敗する側（異常系）も書く。成功する例だけでは、検査が何も検出しなくても通る。

## よいテスト
- 実装でなく、結果（状態）を検証する。
- 1つのテストは1つの事柄。名前で何を保証するか分かるように書く。
- 読みやすさを優先する（テストの中の繰り返しは許す）。
- モックは最小限。本物の関数・データで足りるならそれを使う。

## してはいけないこと
- テストを、スキップ・削除・条件の緩和・期待値の書き換えで通さない（`CONSTRAINTS.md` の Floor）。
- 失敗したテストを、原因を調べずに再実行して通さない。
- 実行していないテストを、通ったと報告しない。

## データの不変条件
件数・必須項目・リンク先の実在など、データが守る条件は、テストにして `npm test` に入れる（例: Editor's Picks の調査データ、台帳、解説の検証状態）。
