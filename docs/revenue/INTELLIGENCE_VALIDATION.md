# OSSALT Intelligence の需要検証（設計のみ・開発しない）

作成：2026-10-09 ／ Revenue Council R9：6役割すべてが RESEARCH。**有料のSaaSは作らない**。

## 1. 競合と差別化

| 既存のサービス | 無料でできること | OSSALTに残る余地 |
|---|---|---|
| GitHub の通知（Watch・Releases） | リリース・リポジトリの更新 | — |
| Dependabot・Renovate | 自社のコードの依存関係の更新・脆弱性 | — |
| OSV・deps.dev | 脆弱性・依存関係の公開データ | — |
| （OSSALT） | — | **SaaSの代わりに入れたOSS（例：n8n・Directus）の、ライセンス変更・開発の停滞・アーカイブ・日本語対応の変化を、エンジニアでない決裁者向けに日本語でまとめる** |

「単なる更新の通知」に企業がお金を払う前提では設計しない。候補の独自の価値は、日本語での影響の整理、複数のOSSの横断、ソース公開型ライセンス（Sustainable Use・MSCL・BUSLなど）の商用での注意点、監査の資料、対応の優先順位。

**批判役の指摘**：これらはサイトにすでにある公開情報の再整理で、まねされやすい。個人の運営するレポートに企業が継続して払う信頼の壁は高い。払う証拠は現時点でゼロ。

## 2. 顧客の課題の仮説（未検証）

- 中小企業の情報システム担当：SaaSから移ったOSSのライセンスが変わったことに気づけない。
- 導入を支援する会社：顧客に入れたOSSの状態を、まとめて報告したい。

## 3. 最小の検証の方法（コードを書かない）

1. 公開データからサンプルのレポートを1本作る（例：「n8n を社内で使うときに確かめること」：ライセンスの種類と変更の履歴、リリースの頻度、アーカイブの有無。**判断は書かない**）。
2. 価格の案と、提供する内容を明記したページに置く。
3. **社名つきの問い合わせの件数**だけを見る。無料の登録数・閲覧数は、払う意思の証拠にしない。
4. 一定期間（運営者が決める）で社名つきの問い合わせがなければ終了。

フォーム・登録・決済は作らない（メールで受ける）。

## 4. 無料と有料の区分の案（仮）

| 無料（サイト） | 有料の候補（需要が確認できた場合のみ） |
|---|---|
| ツールごとのライセンス・更新・スコア（今のサイト） | 指定した複数のOSSの月次のまとめ、変更の日本語での整理、監査用の資料の形式 |

## 5. 開発の費用の見積もり

需要が確認できるまで見積もらない（Phase 5）。今回は0時間。

## 6. AIでできないこと（限界の明記）

- ライセンスの法的な解釈（例：Sustainable Use License のもとでの特定の使い方の可否）は保証できない。
- 脆弱性がないこと・安全であることは保証できない。
- レポートは事実（ライセンスの名前・変更の日・リリースの日など）の提示に限り、判断は利用者と専門家に委ねると明記する。「安全」「適合」とは書かない。
